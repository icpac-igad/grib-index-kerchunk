  The EWC cluster sustained 127 MB/s ≈ 1 Gbps continuously for eight days. That
  is the requirement, and it is the whole problem: at 1 Gbps, 88 TB takes ~200 h
  no matter which tool you use or how many cores you throw at it. Herbie's 143
  h and GIK's 192 h both collapse to the same link-bound floor.

  Latency makes it worse. The job is latency-bound (§A1: 70% CPU idle, readers
  waiting on round trips — 298 ms per message at 789 KB each).
  Nairobi→eu-central-1 adds roughly 150 ms RTT over EWC's European position —
  worth measuring with a ping before trusting this. Per-message cost rises to
  ~450–600 ms, so per-reader rate drops to ~1.6–2.2 msg/s and you need ~75–100 
  concurrent readers instead of 48 just to hold the same throughput. That's ~25
  workers × 2 GB = ~50 GB RAM and maybe 30 cores of real work — trivial for an
  HPC node. The cluster is not the constraint. Holding 100 concurrent TLS
  streams at 1 Gbps to Frankfurt for eight days is.

  Money: ecmwf-forecasts is AWS Open Data, so the 88 TB costs nothing in egress
  charges. The cost is entirely your local link and eight days of it.

  125,970-request/date problem into a 2,470-request/date one. 51x fewer round 
  trips, permanently, for every consumer, on every pass.

  That's what the 200 hours bought. Not a faster download — a different access
  pattern.

  Can Herbie be driven by Dask?

  Yes. FastHerbie already does concurrent downloads, and
  dask.delayed(fetch)(date) across a cluster works fine. Anyone claiming
  otherwise is wrong, and §4.1 of GIK_vs_Herbie_Evaluation.md ("cannot natively
  distribute… without significant custom engineering") oversells it, same as
  §4.2 did.

  But Dask-over-Herbie and Dask-over-a-store are not the same operation:

  Dask over Herbie parallelizes a download. Dask over the store parallelizes a 
  query.

  Concretely, four things don't carry over:

  1. There is no ds. ds.t850.sel(time=slice(...), number=3).mean() builds a
     graph from the manifest with zero I/O and fetches only the chunks that
     selection touches. With Herbie you must write the fetch plan yourself —
     which means knowing what exists, which means parsing 87 .index files per
     date, every run. That's the amortization point from my last answer, and
     it's a startup cost, not a throughput one.
  2. Herbie's cache is worker-local. It downloads to local disk. On a
     distributed cluster each worker has its own filesystem, so the cache
     doesn't help across workers and a retry landing elsewhere is cold. The
     store's chunks are in object storage — shared by construction.
  3. Every run re-decodes. Training reads the corpus once per epoch. Herbie
     decodes GRIB every time, or you materialize to disk yourself — at which
     point you have rebuilt the realization pipeline, without the manifest, the
     repair path, or the commit history.
  4. A pipeline is a program; a store is data. ICPAC can open_zarr with no
     credentials, no eccodes, no AWS account (REALIZED_EA_SWIO_STORE.md:109).
     The Herbie equivalent is handing someone a codebase and a support
     commitment.

  Plus the thing Icechunk gives that neither Herbie nor plain Zarr does:
  commits. A snapshot ID pins exactly which bytes were read. A Herbie run isn't
  versioned — if ECMWF rewrites a file, you have no record.

  Where Herbie genuinely wins

  I'll restate this plainly, because it's real: per stream, Herbie measured 
  faster than GIK (4.53 vs 3.35 msg/s), both move the same 88 TB, and for one
  date or one variable it's simpler and needs no infrastructure. If the only
  consumer were you, and the workload were a single pass, Herbie + Dask would
  have worked and finished sooner. REALIZATION_COST.md §5's "honest summary"
  says this already.

  The structural change, not just the arithmetic

  At EWC the job is latency-bound — which is why my sweep scaled from 19.9 to

  nothing, because the wall is bandwidth, not latency. Every tuning lever
  discussed in this entire conversation — 48 readers, thread counts, eccodes vs
  gribberish — becomes irrelevant. The decoder could be infinitely fast and it
  would change nothing.

  Global Ensemble Prediction Systems (EPS) from ECMWF and NOAA such as IFS,     
  GEFS generate petabyte-scale datasets essential for early warning systems,    
  probabilistic forecasting, and AI/ML weather applications. However, the GRIB  
  format designed for efficient archival storage—resists cloud-native random    
  access patterns. Converting archives to Analysis Ready Cloud Optimized (ARCO) 
  formats would require prohibitive storage duplication. Virtual Zarr datasets  
  enabled by Virtualizarr library offer a transformative alternative:           
  lightweight reference layers exposing original GRIB files through             
  cloud-native interfaces without data conversion.                              
                                                                                
  This approach creates a win-win-win solution. Data producers maintain GRIB    
  files without additional processing. Cloud providers serve data efficiently   
  through byte-range requests. End users access ensemble forecasts via familiar 
  tools (xarray, Dask) as if data were in Zarr format. Previous work on         
  Grib-Index-Kerchunk (https://github.com/icpac-igad/grib-index-kerchunk )      
  method demonstrated this paradigm by exploiting a critical insight: GRIB      
  index files (.idx text for GEFS, .index JSON for ECMWF) contain all byte      
  offset information needed for virtual reference creation. Rather than         
  scanning entire corpus of GRIB files— compute expensive at ~2,400 files per   
  GEFS run or ~85 files of 5GB each for ECMWF—the GIK method reads only         
  lightweight index files (~KB/ few MB each) plus 1-2 sample GRIB files to      
  extract metadata structure. This achieves regional data access with less than 
  5% of original GRIB data read.                                                
                                                                                
   Building on this foundation, we develop GEFS and ECMWF custom parsers        
  following the VirtualiZarr Parser protocol with native Zarr v3                
  ArrayBytesCodec using gribberish, a Rust-based decoder delivering             
  order-of-magnitude performance improvements. Following HRRRparser             
  (https://github.com/virtual-zarr/hrrr-parser ) patterns, our parsers          
  construct chunk manifest store. Virtual references persist to Icechunk        
  transactional storage following zarr specification, enabling                  
  version-controlled datasets where chunks reference original GRIB bytes. The   
  resulting stores integrate with xarray and Dask for parallel ensemble         
  processing across 30-51 members and 85+ forecast timesteps.
